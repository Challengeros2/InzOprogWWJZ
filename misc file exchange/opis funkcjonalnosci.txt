    Prowadzący zajęcia: Artur Samojluk
    Zespół i koncepcja
    projektu
    Utworzenie zespołu, wybór tematu i przygotowanie wspólnego środowiska pracy.
    Cel ćwiczenia
    Przekształcicie pomysł w zwięzły opis projektu informatycznego, określicie jego podstawowe
    funkcjonalności i rozpoczniecie pracę w dwuosobowym zespole. Przygotowana dokumentacja
    będzie punktem wyjścia do kolejnych laboratoriów.
    1. Utwórzcie dwuosobowy zespół
    Dobierzcie się w pary. Zapiszcie imiona i nazwiska, numery indeksów oraz grupę laboratoryjną. Ustalcie
    nazwę zespołu, sposób kontaktu i wstępny podział zadań. Obie osoby odpowiadają za znajomość
    koncepcji oraz aktualność dokumentacji projektu.
    2. Wybierzcie ideę i nadajcie projektowi tytuł
    Zaproponujcie 2-3 pomysły i wybierzcie jeden możliwy do rozwinięcia w semestrze przez dwie osoby.
    Punktem wyjścia powinien być konkretny problem, np. rezerwowanie sal, organizacja wydarzeń lub
    zarządzanie wypożyczeniami.
    Tytuł projektu: [nazwa aplikacji i krótkie określenie jej przeznaczenia]. Przykład: SalaSpot - system
    rezerwacji sal do pracy zespołowej.
    W 8-12 zdaniach opiszcie: jaki problem rozwiązujecie, kto będzie korzystać z aplikacji, jak użytkownik
    radzi sobie obecnie oraz co zyska dzięki Waszemu rozwiązaniu. Dodajcie jeden prosty scenariusz
    użycia od rozpoczęcia działania do uzyskania efektu.
    3. Określcie podstawowy zakres funkcjonalny
    Wypiszcie 5-8 funkcjonalności i nadajcie im identyfikatory F01, F02 itd. Każdą opiszcie z perspektywy
    użytkownika: „Użytkownik może…”. Wskażcie 3-5 funkcji obowiązkowych pierwszej wersji (MVP);
    pozostałe oznaczcie jako rozszerzenia. Zapiszcie również co najmniej 2 elementy poza zakresem
    pierwszej wersji.
    Przykład zapisu funkcjonalności - fragment listy dla systemu rezerwacji sal:
    ID Funkcjonalność Zakres
    F01 Użytkownik może sprawdzić dostępne sale i terminy. MVP
    F02 Użytkownik może zarezerwować wolny termin. MVP
    F03 Użytkownik może anulować własną rezerwację. MVP

    Narzędzia i współpraca
    Przygotujcie jedno wspólne miejsce prowadzenia projektu i jedno repozytorium. Sprawdźcie, czy
    obie osoby mają dostęp do utworzonych zasobów.
    4. LaboChat.com - konto zespołu
    01 Otwórzcie LaboChat.com, załóżcie konto zespołu i skonfigurujcie dostęp dla obu osób.
    02 Przygotujcie wspólne miejsce pracy projektu pod ustalonym tytułem. Zapiszcie nazwę zespołu,
    skład, krótki opis pomysłu oraz odnośnik do repozytorium GitHub.
    03 Zapoznajcie się z dostępnymi sposobami komunikacji, zapisywania ustaleń i organizowania
    pracy. Ustalcie, gdzie zapisujecie decyzje i jak informujecie drugą osobę o postępach.
    04 Zapiszcie co najmniej 4 zadania startowe, np. opis idei, lista funkcjonalności, przygotowanie
    repozytorium i sprawdzenie dostępu. Dla każdego podajcie osobę odpowiedzialną, termin oraz
    stan realizacji. Przydzielcie zadania obu osobom.
    05 Każda osoba dodaje przynajmniej jedno ustalenie lub aktualizację. Odnotujcie zakończenie
    wykonanych zadań.
    5. GitHub - repozytorium projektu
    01 Każda osoba zakłada własne konto na GitHub lub korzysta z istniejącego.
    02 Jedna osoba tworzy publiczne repozytorium przez opcję New repository. Nadajcie krótką nazwę
    powiązaną z tytułem, np. salaspot, dodajcie opis i włączcie utworzenie pliku README.md.
    03 Dodajcie drugą osobę jako współpracownika z możliwością zapisu. Przyjmijcie zaproszenie i
    sprawdźcie, czy obie osoby mogą wprowadzać zmiany.
    04 Uzupełnijcie README.md według karty projektu na stronie 3. Repozytorium jest głównym źródłem
    aktualnej dokumentacji; w LaboChat.com zamieszczajcie linki do odpowiednich materiałów.
    05 Każda osoba zapisuje co najmniej jedną własną, merytoryczną zmianę (commit), np. opis idei
    albo zakres funkcjonalny. Commit utrwala wersję zmian; jego opis powinien wyjaśniać, co zostało
    dodane lub poprawione.
    Efekt tego etapu
    Zespół ma działające środowisko współpracy, repozytorium i pierwszą wersję dokumentacji.
    Implementacja aplikacji będzie rozwijana w kolejnych ćwiczeniach.
    Pomoc: GitHub Docs - utworzenie repozytorium i zapisanie pierwszej zmiany.

    Zespół liczy 2 osoby, a projekt ma uzgodniony tytuł i opis idei.
    Lista obejmuje 5-8 funkcjonalności, oznaczone MVP oraz elementy poza zakresem.
    Konto zespołu w LaboChat.com jest przygotowane; obie osoby mają dostęp i zapisano zadania.
    Publiczne repozytorium zawiera kompletny README.md; obie osoby mają możliwość zapisu.
    Historia repozytorium pokazuje co najmniej jeden merytoryczny commit każdej osoby.
    Linki działają i umożliwiają prowadzącemu sprawdzenie rezultatów pracy.

    zajęć. Obie osoby powinny umieć wyjaśnić ideę, zakres pierwszej wersji i przyjęty podział pracy.

            function updateCartQty(itemId, change) {
                const item = state.currentCart.find(c => c.id === itemId);
                if (item) {
                    item.qty += change;
                    if (item.qty <= 0) {
                        state.currentCart = state.currentCart.filter(c => c.id !== itemId);
                    }
                }
                renderCurrentTicket();
            }

            function renderCurrentTicket() {
                const list = document.getElementById('order-ticket-list');
                const submitBtn = document.getElementById('btn-submit-order');
                const totalEl = document.getElementById('order-total-price');

                if (state.currentCart.length === 0) {
                    list.innerHTML = `<p class="text-slate-400 text-xs italic text-center py-6">Brak pozycji w zamówieniu</p>`;
                    submitBtn.disabled = true;
                    totalEl.innerText = '0.00 PLN';
                    return;
                }

                submitBtn.disabled = false;
                let total = 0;

                list.innerHTML = state.currentCart.map(item => {
                    const subtotal = item.price * item.qty;
                    total += subtotal;
                    return `
                        <div class="flex items-center justify-between border-b border-slate-200 pb-1.5">
                            <div class="flex-grow pr-2">
                                <p class="text-xs font-medium text-slate-800">${item.name}</p>

                                <span class="text-xs font-bold w-4 text-center">${item.qty}</span>

                const emp = document.getElementById('sch-employee').value;
                const loc = document.getElementById('sch-attraction').value;
                const from = document.getElementById('sch-time-from').value;
                const to = document.getElementById('sch-time-to').value;

    3. Idea i problem projektu

    Park rozrywki „Wirgo” to aplikacja informatyczna przeznaczona do kompleksowego zarządzania codziennym funkcjonowaniem parku rozrywki. Głównym problemem, który rozwiązuje projekt, jest konieczność koordynowania wielu procesów związanych z obsługą gości i pracowników. W tradycyjnym sposobie pracy sprzedaż biletów, kontrolowanie wejść na atrakcje, obsługa gastronomii oraz tworzenie grafików mogą być prowadzone za pomocą oddzielnych narzędzi lub dokumentów. Takie rozwiązanie utrudnia przepływ informacji i może powodować pomyłki. Nasza aplikacja umożliwia obsługę najważniejszych procesów w jednym wspólnym systemie. Z systemu będą korzystać kasjerzy, kucharze, technicy, menedżerowie oraz pracownicy odpowiedzialni za kontrolę wejść na atrakcje. Kasjer będzie mógł sprzedawać bilety i karnety, wydawać opaski RFID oraz doładowywać je żetonami. Kucharz otrzyma zamówienia gastronomiczne i będzie mógł aktualizować ich status. Technik będzie kontrolował stan atrakcji, a menedżer będzie zarządzał harmonogramem pracowników. Dzięki aplikacji pracownicy będą mieli łatwiejszy dostęp do aktualnych informacji, a obsługa parku stanie się bardziej uporządkowana.
    4. Użytkownicy i scenariusz użycia
    Główne grupy użytkowników
        Kasjer – sprzedaje bilety, karnety i opaski, a także przyjmuje zamówienia gastronomiczne.
        Kucharz – odbiera zamówienia i aktualizuje ich status.
        Technik – sprawdza stan techniczny atrakcji i aktualizuje ich dostępność.
        Menedżer – przydziela pracowników do stanowisk i tworzy harmonogramy pracy.
        Pracownik bramki – sprawdza opaski RFID i kontroluje możliwość wejścia na atrakcje.
    Przykładowy scenariusz użycia
        Gość przychodzi do parku rozrywki „Wirgo”.
        Kasjer wybiera rodzaj wejściówki i sprzedaje gościowi opaskę z określoną liczbą żetonów.
        Gość wybiera atrakcję, z której chce skorzystać.
        Pracownik bramki wybiera atrakcję w systemie i skanuje identyfikator opaski RFID.
        System sprawdza, czy opaska istnieje w bazie i czy posiada wystarczającą liczbę żetonów.
        System sprawdza również, czy wybrana atrakcja jest sprawna i dostępna.
        Jeżeli wszystkie warunki są spełnione, system pobiera odpowiednią liczbę żetonów i zezwala na wejście.
        Jeżeli warunki nie są spełnione, system wyświetla odpowiedni komunikat.

    1. Cel i zakres wersji v1
    1.1. Cel projektu

    Celem pierwszej wersji aplikacji Park Rozrywki „Wirgo” jest stworzenie systemu umożliwiającego podstawową obsługę gości oraz kontrolowanie najważniejszych procesów zachodzących na terenie parku rozrywki.

    Głównym odbiorcą systemu są pracownicy parku, w szczególności kasjerzy, pracownicy bramek oraz osoby odpowiedzialne za stan techniczny atrakcji. Użytkownik będzie mógł sprzedawać wejściówki, wydawać opaski RFID, doładowywać je żetonami oraz kontrolować możliwość wejścia na poszczególne atrakcje. System umożliwi również sprawdzanie dostępności atrakcji oraz tworzenie zamówień gastronomicznych. Dane będą przechowywane w zaprojektowanej bazie danych, dzięki czemu informacje nie będą znikały po zamknięciu aplikacji. Pierwsza wersja ma zapewnić sprawniejszą obsługę gości i ograniczyć błędy związane z ręcznym kontrolowaniem opłat oraz dostępności atrakcji.
    1.2. Główny odbiorca
        Kasjerzy – sprzedaż wejściówek i obsługa opasek.
        Pracownicy bramek – kontrolowanie wejść na atrakcje.
        Technicy – aktualizowanie stanu technicznego atrakcji.
        Pracownicy gastronomii – tworzenie zamówień.

    3. Struktura bazy danych
    3.1. Założenia

    Baza danych będzie przechowywać informacje o opaskach RFID, atrakcjach parku, doładowaniach, wejściach gości oraz zamówieniach gastronomicznych.

    Każda tabela będzie posiadała własny klucz główny (PK). Klucze obce (FK) będą odpowiadały za powiązania między tabelami.

    Przyjęte typy danych:
        INT – liczba całkowita.
        VARCHAR – tekst.
        DECIMAL – liczba dziesiętna.
        DATETIME – data i godzina.
        DATE – data.
        TIME – godzina.

    erDiagram

    Opis relacji
        Opaska – Doładowanie (1:N): jedna opaska może mieć wiele doładowań.
        Opaska – Wejście (1:N): jedna opaska może być używana do wielu wejść.
        Atrakcja – Wejście (1:N): jedna atrakcja może mieć wiele zarejestrowanych wejść.
        Zamówienie – PozycjaZamowienia (1:N): jedno zamówienie może zawierać wiele pozycji.
        Produkt – PozycjaZamowienia (1:N): jeden produkt może występować w wielu pozycjach zamówień.
        Pracownik – Harmonogram (1:N): jeden pracownik może mieć wiele wpisów w harmonogramie.

    Widok: W01 – Panel kasjera.

    Oczekiwane działanie:

    Kasjer wybiera rodzaj wejściówki, określa liczbę żetonów lub rodzaj karnetu i zatwierdza sprzedaż. System generuje unikalny identyfikator opaski RFID i zapisuje informacje o niej w bazie danych.

    Potrzebne dane:
        Typ wejściówki.
        Numer RFID.
        Liczba żetonów.
        Właściciel opaski.
        Data wydania.

    Warunek poprawnego działania:

    Nowa opaska zostaje zapisana w bazie danych i otrzymuje unikalny identyfikator.

    Sytuacja błędna:

    Jeżeli podano nieprawidłową liczbę żetonów lub identyfikator opaski już istnieje, system wyświetla komunikat o błędzie i nie zapisuje nieprawidłowych danych.
    F02 – Doładowywanie opaski żetonami

    Użytkownik: Kasjer.

    Widok: W01 – Panel kasjera.

    Oczekiwane działanie:

    Kasjer wpisuje identyfikator opaski oraz liczbę żetonów, które chce dodać. System wyszukuje opaskę, sprawdza jej typ i aktualizuje saldo żetonów.

    Potrzebne dane:
        Numer RFID.
        Aktualne saldo.
        Liczba dodawanych żetonów.
        Data doładowania.

    Warunek poprawnego działania:

    Saldo opaski zostaje zwiększone o podaną liczbę żetonów, a operacja zostaje zapisana w historii doładowań.

    Sytuacja błędna:

    Jeżeli opaska nie istnieje, jest nieaktywna lub posiada karnet czasowy, system nie wykonuje doładowania i wyświetla odpowiedni komunikat.
    F03 – Tworzenie zamówień gastronomicznych

    Użytkownik: Kasjer lub pracownik gastronomii.

    Widok: W04 – Panel gastronomii.

    Oczekiwane działanie:

    Użytkownik wybiera produkty z menu, określa ich ilość, a system automatycznie oblicza wartość całego zamówienia. Po zatwierdzeniu zamówienie zostaje zapisane w bazie danych.

    Potrzebne dane:
        Lista produktów.
        Ceny produktów.
        Ilości produktów.
        Data utworzenia zamówienia.
        Łączna wartość zamówienia.

    Warunek poprawnego działania:

    Zamówienie zawierające co najmniej jedną pozycję zostaje zapisane w bazie danych wraz z prawidłową sumą.

    Sytuacja błędna:

    Jeżeli użytkownik próbuje zatwierdzić puste zamówienie lub podaje nieprawidłową ilość produktu, system wyświetla komunikat i nie zapisuje zamówienia.
    F05 – Zarządzanie stanem technicznym atrakcji

    Użytkownik: Technik.

    Widok: W03 – Panel technika.

    Oczekiwane działanie:

    Technik przegląda listę atrakcji, sprawdza ich aktualny stan techniczny i może zmienić status atrakcji na „W trakcie naprawy” lub „Działająca”.

    Potrzebne dane:
        Identyfikator atrakcji.
        Nazwa atrakcji.
        Aktualny status.
        Nowy status.

    Warunek poprawnego działania:

    Zmiana statusu zostaje zapisana w bazie danych i jest widoczna również w panelu bramki.

    Sytuacja błędna:

    Jeżeli atrakcja nie istnieje, system nie wykonuje zmiany i wyświetla komunikat o błędzie.
    F07 – Weryfikacja opasek RFID i kontrola wejścia na atrakcje

    Użytkownik: Pracownik bramki.

    Widok: W02 – Panel bramki.

    Oczekiwane działanie:

    Pracownik wybiera atrakcję i wpisuje lub skanuje identyfikator opaski RFID. System sprawdza, czy opaska istnieje, czy jest aktywna, czy atrakcja działa oraz czy gość posiada odpowiednią liczbę żetonów.

    Jeżeli warunki są spełnione, system zezwala na wejście i pobiera odpowiednią liczbę żetonów. W przypadku karnetu czasowego system nie pobiera żetonów, o ile karnet jest ważny.

    Potrzebne dane:
        Numer RFID.
        Typ opaski.
        Saldo żetonów.
        Identyfikator atrakcji.
        Koszt wejścia.
        Status techniczny atrakcji.
        Data i godzina wejścia.

    Warunek poprawnego działania:

    System zezwala na wejście, jeżeli opaska jest aktywna, atrakcja jest sprawna i dostępne jest odpowiednie saldo lub ważny karnet. Operacja zostaje zapisana w historii wejść.

    Sytuacja błędna:

    Jeżeli opaska jest nieznana, nieaktywna, saldo jest niewystarczające lub atrakcja jest niedostępna, system blokuje wejście i wyświetla odpowiedni komunikat.
